# Агентная разработка

Рабочий набор для проекта: постоянные правила в [AGENTS.md](../AGENTS.md), шесть проектных навыков, существующие инструменты общего назначения и проверки по риску изменения. Правила и навыки версионируются в репозитории вместе с архитектурой.

## Что хранить в разных местах

| Место | Содержание |
|---|---|
| `AGENTS.md` в корне | Состояние проекта, границы слоёв, инварианты, порядок проверки и работа с Git |
| `.agents/skills/<name>/SKILL.md` | Workflow конкретного типа задачи, его входы и критерии проверки |
| `docs/architecture.md`, профильные документы | Подробная архитектура и сценарии без копирования во все навыки |
| `CONTEXT.md` | Термины и различия сущностей предметной области |
| `docs/adr/` | Решение, альтернативы, последствия и статус архитектурного выбора |
| Будущие локальные `AGENTS.md` | Команды и особые ограничения реально созданного приложения, пакета или сервиса |
| CI и проектные скрипты | Автоматически исполняемые проверки, появляющиеся вместе с кодом |

Codex загружает постоянные инструкции из `AGENTS.md`, а навыки выбирает по описанию задачи; репозиторные навыки размещаются в `.agents/skills`. Поэтому инструкции не требуют подключения всех workflows к каждой задаче. См. официальные руководства по [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md) и [навыкам](https://learn.chatgpt.com/docs/build-skills).

Новые локальные инструкции добавляются, когда появляется соответствующий код и проверенные команды. Пока Flutter/Dart и сервисы не реализованы, не создаём пустые деревья приложений и дублирующие инструкции для них.

## Проектные навыки

| Навык | Когда применять | Проверяемый результат |
|---|---|---|
| [analyses-flutter-feature](../.agents/skills/analyses-flutter-feature/SKILL.md) | Экран или независимая функция Flutter | MVVM, явные состояния, зависимости через интерфейсы, доступность и адаптивность |
| [analyses-medical-data](../.agents/skills/analyses-medical-data/SKILL.md) | Результаты, единицы, даты, словари, специальности, МКБ | Воспроизводимое преобразование с исходными данными, редакциями и неоднозначностями |
| [analyses-offline-sync](../.agents/skills/analyses-offline-sync/SKILL.md) | База, миграция, очередь и синхронизация | Сохранение без сети, восстановление после сбоя, идемпотентность и разрешение конфликтов |
| [analyses-cloud-service](../.agents/skills/analyses-cloud-service/SKILL.md) | API, worker, коннектор сайта, уведомления или подписка | Граница владения, совместимый контракт, проверка доступа и поведение повторов |
| [analyses-document-ai](../.agents/skills/analyses-document-ai/SKILL.md) | OCR/ASR/LLM и парсинг документов | Черновик с происхождением, явный режим обработки, измеренное качество |
| [analyses-original-storage](../.agents/skills/analyses-original-storage/SKILL.md) | Оригиналы и облачное S3/SeaweedFS-хранилище | Неизменные байты, проверенная финализация, квоты и восстановление |

Примеры сочетаний: импорт и распознавание документа использует навыки UI, хранения и AI; изменение единиц результата — медицинские данные и локальную миграцию при изменении схемы. Один навык не соответствует одному агенту или микросервису.

Навыки содержат проектные решения и характерные сбои. Синтаксис языка, справочник Flutter и общие рекомендации по написанию кода в них не дублируются.

## Готовые навыки и официальные источники

Для разработки Flutter/Dart стоит подключить выбранные официальные workflows из [flutter/agent-plugins](https://github.com/flutter/agent-plugins) или [dart-lang/skills](https://github.com/dart-lang/skills). Flutter перечисляет эти источники в [документации инструментов для агентов](https://docs.flutter.dev/ai/tools).

Установленный базовый набор:

| Задача | Официальные навыки |
|---|---|
| Структура Flutter | `flutter-apply-architecture-best-practices` |
| Адаптивный UI и исправление layout | `flutter-build-responsive-layout`, `flutter-fix-layout-issues` |
| Проверки | `dart-run-static-analysis`, `dart-add-unit-test`, `flutter-add-widget-test`, `flutter-add-integration-test` |
| Навигация и языки интерфейса | `flutter-setup-declarative-routing`, `flutter-setup-localization` |
| Сериализация транспортных моделей | `flutter-implement-json-serialization` |

Десять официальных навыков установлены в репозиторий с фиксацией upstream-ревизий и хешей в [lock-файле](../.agents/official-skills.lock.json). Источники, лицензии и особенности применения описаны в [окружении разработки](development-environment.md). Рекомендации примеров по state management или code generation сверяются с проектными ADR, а не становятся решением автоматически.

Для локального AI позже могут понадобиться `dart-setup-ffi-assets` и `dart-use-ffigen`: подключать после выбора C ABI/FFI backend. Сейчас они не установлены.

Из уже доступных в среде навыков полезны:

- `codebase-design` и `domain-modeling` — границы модулей, интерфейсы, терминология и ADR.
- `diagnosing-bugs` — воспроизведение и проверка причин ошибок.
- `tdd` — задачи, для которых выбран подход test-first.
- `docker-authoring` — контейнеры сервисов, AI runtime и SeaweedFS.
- PDF-навык — создание и визуальная проверка экспортируемых PDF-отчётов.
- UI/UX-навык — работа над дизайном и доступностью интерфейса.
- Навыки security review — когда задача включает соответствующую проверку кода, прав доступа или внешних границ.

Это доступные инструменты среды, а не зависимости проекта. Если навык отсутствует у другого разработчика, обычная реализация продолжается по репозиторным инструкциям. Специализированные аудиты не являются обязательным этапом каждой правки.

## Инструменты разработки

Установлены Flutter 3.50.0 / Dart 3.14.0, команды доступны в `PATH`; подключён проектный Dart/Flutter MCP. Анализ, тест и web-сборка проверены на временном приложении вне репозитория. Состояние Android/Xcode и однократные действия пользователя описаны в [окружении разработки](development-environment.md). В самом проекте `pubspec.yaml` и клиентские/серверные пакеты ещё отсутствуют.

Для первого рабочего среза:

1. Использовать зафиксированный SDK из `.flutter-version`; определить минимальные версии целевых платформ.
2. Создать минимальный клиент и чистый Dart-пакет медицинской модели, определить команды проверки. Структуру workspace расширять по появлению кода.
3. Использовать настроенный [Dart/Flutter MCP server](https://docs.flutter.dev/ai/tools) для диагностики, анализа, тестов и работы с созданным приложением. Доступные команды сверять с реальным `tools/list` сервера.
4. Перенести проверенные команды в CI и ближайшие `AGENTS.md`. Версии инструментов и зависимости должны воспроизводиться в чистом checkout.
5. Проверить выбранный вертикальный сценарий на web и мобильных платформах; платформенные адаптеры камеры, файлов, геопозиции и локального AI оценивать на соответствующих устройствах.

Необходимость MCP определяется задачей: он даёт агенту инструменты, но не заменяет SDK, тесты, навыки и инструкции. Настройки MCP и пути к SDK зависят от окружения; не сохраняем неработающий локальный путь или секреты в репозиторий.

## Порядок выполнения задачи

1. Уточнить результат по поручению и коду: пользовательское поведение, затронутый модуль, необходимые совместимость и проверки. Пробелы, не мешающие безопасной реализации, решать в рамках существующих соглашений.
2. Прочитать применимые инструкции и навыки. Найти владельца модели и данных, существующие интерфейсы и тесты.
3. Для изменения публичной границы сначала описать контракт: входы, результат, ошибки, повторы, версии и права. Обновить ADR при существенном архитектурном выборе.
4. Реализовать связный вертикальный сценарий. Сначала использовать уже существующие зависимости и интерфейсы; выделять новый пакет или сервис при появлении самостоятельной ответственности.
5. Выполнить проверки из следующей таблицы по области изменения. Исправить выявленные ошибки и просмотреть итоговый diff.
6. Обновить относящуюся документацию. Сообщить результат, фактически выполненные проверки и оставшиеся ограничения. Коммит и публикация следуют поручению пользователя.

Задание агенту удобно задавать так:

```text
Результат: какое действие пользователя или интеграции должно заработать.
Область: существующие пакеты/сервисы и разрешённые изменения контрактов.
Ограничения: offline, платформы, совместимость и режим AI по задаче.
Приёмка: наблюдаемое поведение и существенные сбои.
Доставка: нужны ли коммит, PR или развёртывание.
```

## Проверки по типу изменения

| Изменение | Достаточная основа проверки |
|---|---|
| Документация и навыки | Ссылки, YAML-метаданные навыков, согласованность с архитектурой, `git diff --check` |
| Медицинские правила | Детерминированные unit-примеры: исходные значения, единицы, сравнения, даты и неоднозначные соответствия |
| MVVM/UI | Переходы ViewModel и widget-поведение затронутого сценария; адаптивность, клавиатура и доступность по изменению |
| Локальная схема | Миграция с поддерживаемой старой версией, перезапуск, целостность данных; для web — браузерное хранение |
| Синхронизация | Нет сети, потеря ответа, повтор, конфликт, удаление и восстановление очереди; транзакция данных с outbox |
| API и очереди | Контракт клиента/потребителя, доступ к чужому профилю, повторная доставка, таймаут и совместимость схем |
| Оригиналы | Сравнение исходного SHA-256 после скачивания, повтор финализации, обрыв между объектом и БД, квоты и доступ |
| OCR/LLM | Фиксированный обезличенный набор, точность полей, ошибки единиц/дат, неподтверждённые значения и provenance |
| Native-интеграция/FFI | Сборка затронутых платформ; реальный runtime там, где поведение зависит от устройства |
| Подписки | Проверка прав сервером, повторы callback/webhook, восстановление покупки и независимость локальных сценариев |

Тесты должны различать правильное и ошибочное поведение. Покрытие строк и снимок текущего ответа модели сами по себе не подтверждают корректность. Тяжёлые проверки добавляются при соответствующем риске; проверки на всех устройствах не требуются для изменения текста.

## Если понадобится несколько агентов

Делегирование используется по явному поручению. До разделения работы фиксируются контракт, файлы каждого участника и критерии результата. Независимую реализацию можно вести по функциям UI, адаптерам или workers; общую схему БД, протокол синхронизации и публичный контракт одновременно меняет один ответственный.

Координатор объединяет результат, проверяет совместимость и выполняет итоговые проверки. Ревью можно отделить от реализации. Количество агентов определяется независимостью задач, а не числом навыков.
