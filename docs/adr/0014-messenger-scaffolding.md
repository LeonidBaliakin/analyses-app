# ADR 0014: Каркас каналов мессенджеров с имитацией доставки

Статус: принято для каркаса, 26.11.2026. Реальная отправка не реализована.

## Контекст

Нужно подготовить Telegram, VK и MAX к независимому подключению, сохранив
локальную работу приложения и не создавая внешних эффектов. Общая архитектура
предусматривает orchestrator и отдельные delivery workers.

## Решение

Notifications владеет своей PostgreSQL БД с simulation bindings, intent,
логическими очередями по channel, leases, receipts и transactional outbox.
Отдельные worker containers одного Dart AOT-образа используют разные ключи и
адаптеры через HTTP. Режимы только disabled/dry_run. Internal network workers
не имеет выхода в интернет; токены и адресаты провайдеров отсутствуют.

Фиксированные RU/EN шаблоны не содержат медицинских данных и произвольного текста.
simulationOnly обязателен на binding/job. Результат имитации — simulated;
unknown терминален для автоматики. Стабильный notificationId и attempt receipts
делают повторы HTTP безопасными; exactly-once эффект внешнего API не обещается.

Compose profile messengers и Ansible opt-in включают БД, миграции, образы,
persistent secrets и readiness. Публичные webhook handlers, пользовательский
opt-in, business publishers, live delivery и мониторинг — следующий этап.

## Альтернативы и последствия

- Встраивание HTTP мессенджеров в Records/Processing связывает медицинскую
  транзакцию с провайдером и смешивает ответственность; отклонено.
- Брокер и отдельная БД каждого канала сразу усиливают изоляцию, но добавляют
  инфраструктуру до появления интеграций; отложено. Общая Notifications БД —
  признанная общая точка отказа, при росте очередь можно заменить за API.
- Настоящий sender с фиктивными токенами легко включить случайно; выбран
  fail-closed scaffold без реализации live и внешнего egress.
