# ADR 0012: аккаунты по email и сессии устройств

Статус: принято для первого рабочего среза, 26 ноября 2026 года.

## Контекст

Documents и Records использовали bootstrap bearer из закрытого файла. Требуются
регистрация, вход, восстановление доступа и второе устройство, без мессенджеров.
Локальная медицинская база должна открываться без сети и входа.

## Решение

Отдельный Dart/Shelf `services/identity` владеет собственной PostgreSQL БД:
проверенными email, password verifiers, одноразовыми challenges, сессиями и почтовым
outbox. Documents проксирует только `/v1/auth/*`. Documents и Records проверяют
каждую сессию через закрытый `/internal/session` с сервисным ключом; чужие таблицы
не читаются, проверка не кешируется. Недоступность Identity закрывает облачный
доступ, не локальную работу. Старый явно настроенный bootstrap остаётся для
совместимости development-стенда, но не становится пользовательским аккаунтом.

Регистрация сначала отправляет код; аккаунт создаётся только после проверки кода
и выбора пароля. Запрос восстановления имеет тот же нейтральный ответ для
неизвестного адреса. Код: восемь случайных цифр, 15 минут, не более пяти попыток,
однократное использование. Сброс пароля меняет verifier и отзывает все прежние
сессии одной транзакцией; автоматического входа после сброса нет. Гонка с входом
проверяет verifier под блокировкой строки пользователя.

Пароли: 15–128 Unicode code points, без обрезки пробелов и правил композиции;
PBKDF2-HMAC-SHA256, 600 000 итераций, независимая случайная соль 32 байта.
Вычисление идёт в isolate, одновременно не более четырёх. Сессия: случайные
32 байта, абсолютный срок 30 дней; БД хранит SHA-256 токена. Отзыв одной/всех
сессий действует при следующем серверном запросе. Нет refresh-token протокола.

Web использует HttpOnly/SameSite=Lax cookie; по умолчанию Secure и префикс
`__Host-`. Только loopback development использует cookie без Secure. BrowserClient
включает credentials; CORS разрешает точные origins. Мутации с cookie требуют
`X-App-Request: 1`; браузерные credentials не сохраняются в JS storage и не
возвращаются в JSON. Native получает bearer, хранит его через flutter_secure_storage.
Android исключает shared preferences из backup/transfer; Keychain iOS использует
ThisDeviceOnly. macOS использует собственный legacy Keychain без sharing entitlement.
Ошибка secure storage показывается; plaintext fallback отсутствует.

Лимиты сохраняются в PostgreSQL: четыре письма на адрес / 15 минут, 12 входов на
адрес / 15 минут, 150 мутаций на адрес клиента / 15 минут. Клиентский адрес берётся
из реального соединения с Documents, пользовательские forwarding headers игнорируются.
За reverse proxy несколько пользователей могут делить этот лимит; доверенный proxy
и его отдельная защита требуют настройки перед публичным запуском.

Challenge и зашифрованное AES-GCM письмо фиксируются атомарно. SMTP worker повторяет
один код после отказа. Потеря подтверждения SMTP может дать второе письмо с тем же
кодом; exactly-once доставка не обещается. После доставки payload очищается.
Ключ шифрования outbox хранится в persistent server secrets, отдельно от БД.

У каждого аккаунта пока один профиль `local-profile`, изолированный по ownerId.
Documents/Records идемпотентно создают собственную область при первом обращении,
не перезаписывая существующий отзыв прав/квоту. Подключение синхронизации — отдельная
кнопка с описанием передачи локальных записей. Существующая привязка SQLite к
аккаунту/серверу сохраняется. Оригиналы используют стабильный ownerId в destination,
а не меняющийся токен. Для web передаётся ожидаемый ownerId: изменение cookie в
соседней вкладке не позволяет отправить документы предыдущего аккаунта новому.

Все серверные процессы — Compose, сборка Identity — AOT/non-root, readiness —
реальный запрос к PostgreSQL. Ansible добавляет новые секреты без ротации старых.
Mailpit — явно тестовый приёмник; внешний SMTP не включается автоматически.

## Альтернативы

- Keycloak/OIDC с Authorization Code + PKCE: стандартные федерация, MFA и готовые
  account flows, но добавляет отдельный продукт, redirect/callback контракты и
  платформенную интеграцию. Оставлен как вариант следующего развития.
- Продолжать раздавать bootstrap-токены: не обеспечивает регистрацию и восстановление.
- JWT без запроса к Identity: меньше обращений, но требует отдельного механизма
  немедленного отзыва. Для этого среза выбран простой проверяемый opaque bearer.

## Пределы

Это первый email/password срез, не законченная публичная IAM-платформа. Не добавлены
MFA/passkeys/социальный вход, смена email, удаление аккаунта, семейные профили,
миграция bootstrap-владельца в новый аккаунт, блоклист утёкших паролей, очистка
старых challenges/сессий и пользовательский журнал входов. HTTPS ingress, реальный
SMTP, резервное восстановление и native-хранилища на устройствах проверяются отдельно.
Подписки и врачебные разрешения не входят в этот этап. Локальные медицинские данные
не шифруются этой задачей; завершение сессии не удаляет их с устройства.
