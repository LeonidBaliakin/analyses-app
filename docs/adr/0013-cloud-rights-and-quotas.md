# ADR 0013: облачные права и квоты

Дата: 26 ноября 2026. Статус: принято для первого рабочего среза без платежей.

## Решение

`services/entitlements` владеет отдельной PostgreSQL БД с версионируемой политикой
аккаунта: независимые sync/storage/processing разрешения, срок действия и лимиты.
`packages/cloud_access` содержит общий версионируемый контракт и HTTP-адаптер без
Flutter, FFI и прямых IO/browser импортов. Identity устанавливает владельца;
Entitlements не хранит медицинские записи и не читает таблицы соседних сервисов.

Documents, Records и Processing получают актуальную политику через закрытый HTTP
с сервисным ключом. Прямое пользовательское изменение политики отсутствует.
Административный grant использует отдельный ключ, operationId, ожидаемую revision,
receipt и транзакционный CloudPolicyChanged outbox. Повтор не меняет политику ещё
раз; другой payload под прежним ID или устаревшая revision отвергаются. API не имеет
публичного host-порта, наружу через Documents доступна только сводка своего аккаунта.

Пилотные значения нового аккаунта: 10 000 активных записей, 1 ГиБ оригиналов,
100 успешных серверных распознаваний за календарный месяц UTC; все три права включены,
срок не ограничен. Это техническая стартовая политика, а не купленная подписка.
Меняется административным grant, в том числе до нулевого лимита/отзыва/срока действия.

Usage принадлежит владельцу ресурса и фиксируется его транзакцией:

- Records: число активных записей владельца, включая профиль, курсы и измерения.
  Новая запись и восстановление tombstone увеличивают расход. Правки, удаления и
  повторы не увеличивают его. Блокировка владельца сериализует параллельные создания,
  включая разные профили. История/change log/receipts не входят в этот числовой лимит.
- Documents: ready bytes и резерв загрузок. Повтор reserve не резервирует второй раз;
  finalize переводит резерв в used вместе с ready и outbox. Просроченный staging
  освобождает резерв прежним cleanup. Уменьшение квоты не удаляет оригиналы; ранее
  принятые резервы можно завершить при действующем праве хранения.
- Processing: один slot на jobId. Job и reserved slot создаются атомарно под
  блокировкой владельца. Ready переводит slot в used вместе с draft/outbox. Ошибка
  или отмена переводит reserved в released. Replay jobId не получает новый slot,
  включая новый месяц. Месяц закрепляется серверными часами PostgreSQL при приёме;
  завершение после границы месяца относится к месяцу резерва. Снижение лимита не
  отменяет уже зарезервированную работу, но отзыв самого права прекращает её.

Сервер повторно проверяет право на мутациях, в том числе на replay. Processing также
проверяет его перед исполнением и в cancellation checks. При сбое Entitlements новые
операции закрываются с явной ошибкой, локальное сохранение не блокируется. Открытое
задание может завершиться ошибкой проверки и освободить резерв; скрытого внешнего AI
fallback нет. Чтение готовых оригиналов, облачных записей и сохранённых AI-черновиков
сохраняется при действующей сессии/доступе к профилю. Sync-access при сбое policy может
вернуть canWrite=false с неизвестным лимитом, не препятствуя pull.

Processing PostgreSQL schema 1→2 добавляет ledger без перезаписи jobs/артефактов:
текущая очередь резервируется в месяце миграции, законченные старые работы относятся
к `legacy` и не списываются задним числом из текущего месяца. Повтор migrate не создаёт
новых резервов. SQLite и медицинский codec не меняются.

Старые локальные can_write/cloud_enabled остаются дополнительным аварийным запретом;
GET политики не восстанавливает эти флаги. Legacy standalone constructor без policy
adapter оставлен для совместимости development/tests; оба поддерживаемых Compose
и Ansible включают policy backend явно. Отключение настроенного backend не является
разрешением операции.

UI показывает разрешения, лимиты, used/reserved, месяц и срок в аккаунте. Сводка
получается из трёх API и не обещает атомарного снимка всех сервисов. При сбое обновления
старые значения помечаются устаревшими. UI не является источником полномочий.
Локальные записи, outbox, оригиналы и экспорт доступны независимо от облачных прав.

## Альтернативы

- Общая БД или чтение чужих таблиц: отвергнуто из-за владения данными.
- Центральный quota ledger на каждый upload/job: потребовал бы distributed
  reservation/commit/reconciliation с потерянными ответами. В этом срезе достаточно
  owner-wide лимитов, а атомарный расход остаётся в БД фактического ресурса.
- Только клиентская проверка: не защищает повторы, параллельные устройства и прямой API.
- Подписанные долгоживущие entitlement-токены: отзыв потребовал бы дополнительного
  протокола/задержки; выбран актуальный server-to-server запрос.

## Пределы

Нет оплаты, магазинов, webhook платежей, восстановления покупки, UI администратора,
очистки истории и гарантированного объёма всех служебных БД. Original quota считает
только исходные байты, sync quota — число активных записей; OCR/история/backup не входят
в эти единицы. Лимиты не заменяют технические ограничения размера файла и очереди.
Отзыв действует при следующей проверке; общей транзакции policy и ресурса нет,
поэтому операция с уже полученным разрешением может закончиться одновременно с отзывом.
