# ADR 0011: отчёт за период и синхронизация подтверждённых записей

Дата: 25 ноября 2026 года. Статус: принято для первого рабочего среза пункта 6.

## Решение

`medical_domain.HealthReport` строит согласованный снимок подтверждённых локальных
записей за включительный календарный период. Результаты и измерения включаются по
своей исходной дате; курс — при пересечении периода, даже если начат раньше него.
Профиль входит целиком. Удаления исключены; черновики распознавания не являются
медицинскими записями. Значения, единицы и референсы не преобразуются.

Предыдущий результат показывается только внутри периода при совпадении явно
подтверждённых ID показателя/единицы/выпуска и исходных лаборатории, материала,
метода. Непривязанные названия, неизвестные единицы и неполный контекст
лаборатории/материала/метода не объединяются. Для наблюдений
за один день без времени порядок не угадывается: сводка показывает все последние
значения на эту дату, сравнение неоднозначных дат не выводится. Клинические нормы,
статусы здоровья, интерполяция и преобразование единиц не добавляются.

UI сохраняет выбранный период и в web/desktop экспортирует самодостаточный UTF-8 HTML с экранированным
содержимым для просмотра/печати. Экспортируется один снимок; изменение записи после
нажатия не меняет уже созданный файл. Язык меняет подписи, а не медицинские строки.
На Android/iOS выбор файла в текущем file_selector недоступен: показывается явное
состояние и доступно копирование текста отчёта по действию пользователя.
PDF, ограниченные ссылки для врача и серверное хранение отчётных снимков отложены.

`record_sync` — отдельный чистый Dart API/Storage-контракт. Сериализация записей
форматов 1/2/3 перенесена сюда без изменения старых payload и request outbox;
`local_store` сохраняет прежний вход codec. IO, HTTP и SQL остаются в адаптерах.

`health-records-sync` реализован пакетом `services/records`, владеет отдельной БД
`records` и доступен через Documents proxy. Исходники/байты документов и OCR ему
не принадлежат. Синхронизация записи с documentSource сохраняет происхождение,
но не означает, что оригинал доступен на втором устройстве.

SQLite schema 5 добавляет привязку профиля, стабильный deviceId, серверные версии,
курсор, неизменяемые подготовленные запросы, подтверждения и конфликты. Старый outbox
сохраняется как журнал идемпотентности. Локальные изменения продолжают фиксироваться
с историей/outbox одной транзакцией, без сети/подписки. Подтверждение облака хранится
отдельно; число ожидающих не скрывается после ошибки.

Привязка включает endpoint, владельца и профиль. Смена владельца/хранилища для того же
локального профиля отвергается. Токен хранится только в памяти; после перезапуска нужно
подключиться снова. Сервер проверяет bearer, профиль и собственное can_write; Documents
дополнительно проверяет текущие права профиля и запрет облачных записей.

Сначала клиент получает изменения, затем отправляет outbox по порядку ревизий
(профиль первым), затем получает изменения ещё раз. Серверная версия независима от
локальной. При первом отправлении фиксируются baseVersion/deviceId/operationId и
точный payload; повтор не пересчитывает базу. Потерянный ответ восстанавливается
повтором или собственным событием при pull. Повтор под тем же ключом с другим
содержимым запрещён. Сервер атомарно пишет запись, receipt, change log и outbox.

Счётчик change log назначается под блокировкой профиля в той же транзакции:
последовательность курсора соответствует порядку commit, а не выдаче bigserial
до commit. Pull ограничен 100 событиями и 3 МиБ; применение страницы и курсор
фиксируются одной SQLite транзакцией. Epoch обнаруживает замену серверной истории;
восстановление старого backup требует смены epoch оператором. Автоматического
слияния независимых восстановленных историй пока нет.

Конфликт — несовпадение baseVersion с текущей серверной версией или приход новой
серверной версии при локальных неотправленных правках. Локальная запись остаётся,
серверная версия сохраняется отдельно, отправка этой записи приостанавливается.
Другие записи могут продолжать обмен. Пользователь выбирает локальную либо серверную
версию; обе остаются в журналах. Проверяются обе показанные ревизии. Выбор локальной
создаёт новую операцию против выбранной серверной версии; опоздавший ответ уже
замещённой операции не создаёт конфликт заново. Новая гонка на сервере снова даёт
конфликт. Время устройства не выбирает победителя. Tombstone конфликтует с правкой;
восстановление после серверного удаления возможно только явным выбором локальной версии.

Обмен включается явно, автоматический опрос — раз в 30 секунд, пока приложение живо
и токен доступен. Временные ошибки получают сохранённую задержку 2, 4, 8…300 секунд;
явный повтор может обойти задержку. 401/403, неизвестная схема, другая история сервера
останавливают автоматические попытки, не удаляя данные. ОС может остановить приложение;
фоновые системные задания не обещаются.

## Альтернативы и пределы

- Last-write-wins по часам устройства отвергнут: может незаметно потерять подтверждённые
  значения и удаления.
- Перезапись локальной БД облачным snapshot отвергнута: теряет офлайн-правки/outbox.
- Автоматическое слияние полей отложено: первый срез показывает две полные версии.
- Отдельные несовместимые серверные DTO отвергнуты; используется тот же чистый codec.

Сервис имеет Dockerfile, серверный Compose, профиль development Compose и Ansible
по ADR 0010. Bootstrap авторизация остаётся пилотной, без публичной регистрации,
платежей или врача с отдельными правами. Синхронизируются профиль, результаты,
курсы и измерения; байты оригиналов, OCR/draft history, настройки и история локальных
правок, замещённых до подтверждения облаком, отдельно не синхронизируются. Локальная
история сохраняется; серверный change log содержит только принятые им версии.

Удаление истории, смена аккаунта, длительные offline retention/compaction, push/websocket,
field merge, клинические выводы, PDF и боевой backup/restore требуют следующих срезов.
