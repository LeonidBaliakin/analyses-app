# ADR 0009: общий черновик OCR/LLM и явное подтверждение

Дата: 24 ноября 2026 года. Статус: принято для первого рабочего среза.

## Контекст

Пункт 5 требует получить один тип проверяемого черновика в локальном и собственном
серверном режимах. Оригиналы уже сохраняются по ADR 0008; словарь по ADR 0007
предлагает соответствия, которые пользователь выбирает явно. Ошибки OCR и LLM
не должны создавать подтверждённые медицинские данные.

## Решение

`packages/document_processing` — чистый Dart-контракт задания, черновика,
нормализации и подготовки подтверждения. Он не импортирует Flutter, IO или модели
инференса. Два адаптера возвращают один DTO `schemaVersion: 1`; общий валидатор
проверяет версию runtime, исходные фрагменты и полноту схемы. Нормализация обоих
режимов выполняется этим пакетом в клиенте после извлечения полей. Серверный
worker не содержит отдельной копии медицинских правил.

Первый реальный runtime: Tesseract rus+eng → Qwen2.5-1.5B-Instruct Q4_K_M через
собственный llama.cpp. Фиксируются SHA-256 весов, версии OCR, языковых данных,
llama.cpp, worker, prompt и словаря. Установка весов явная, вне Git. Это
воспроизводимый development runtime, а не выбор окончательной медицинской модели.
[Измерения и ошибки](../reports/processing-pilot-2026-11-24.md).

Локальный адаптер запускает установленный helper на desktop и обращается к
loopback LLM; сеть и подписка для него не требуются. В web, Android и iOS этот
локальный адаптер сообщает недоступность. Серверный режим выбирается отдельно;
клиент сначала сохраняет оригинал через Documents и затем отправляет ID задания.
`services/processing` владеет собственной PostgreSQL БД заданий и производных.
Доступ к оригиналу получает через Documents API под правами отправителя;
не читает таблицы Documents и S3 напрямую. Documents проксирует Processing API
под прежним клиентским endpoint. В development оба режима используют один
llama-server на Mac; серверный OCR/очередь выполняются в Docker.

Состояния: queued → ocr → extracting → ready либо failed/cancelled. Клиент
сохраняет OCR и версии до LLM, черновик, правки и историю в SQLite schema 4.
На сервере очередь сохраняется в PostgreSQL; после перезапуска прерванное задание
возвращается в queued с тем же ID и runtime. Один лидер удерживает session advisory
lock; это простой worker без масштабирования на несколько реплик. Другой runtime
требует нового задания. Повтор запроса того же задания проверяет fingerprint.

Каждая строка разделяет неизменяемые исходные поля, страницу/позиции, ошибки и
редактируемые поля. Слова OCR дополнительно содержат bounding box и confidence.
Evidence выбирается из реальных строк OCR по извлечённому названию; поля, которых
в нём нет, остаются отклонёнными предложениями и не заполняют поля проверки.
Неизвестная дата не заменяется текущей. Отдельно проверяется целый числовой токен,
включая знак сравнения и точность. Это проверка соответствия OCR, а не доказательство
правильности самого OCR или семантики значения. Пропущенные строки можно добавить
вручную с пустым source. При сбое LLM можно продолжить из сохранённого OCR.

Только действие «Подтвердить и сохранить» создаёт LabResult. В одной SQLite
транзакции записываются результаты, история, outbox и маркер подтверждения.
Повтор с тем же operation ID возвращает прежние ID. Первый срез разрешает одно
подтверждение оригинала на профиль: повторный разбор не добавляет второй набор
результатов; исправление подтверждённого результата идёт через редактор записей.
Подтверждённая запись хранит ссылку на оригинал/SHA, job, редакцию черновика и
исходные поля; payload формата 3. Старые форматы 1/2 и их outbox сохраняются.
Сервер публикует производное событие DraftReady, медицинские записи не создаёт.

## Альтернативы

- Отдельные клиентская и серверная модели черновика: отвергнуты из-за расхождения
  проверок, нормализации и поведения подтверждения.
- Только мок OCR/LLM: недостаточно для проверки качества и ресурсов; моки остаются
  в проверках отказов, реальные runtime проверяются на фиксированном наборе.
- Сразу mobile FFI/плагины и внешний AI API: отложены до выбора целевых устройств,
  приемлемых моделей и явного согласия на внешний режим.
- Автоматическое сохранение распознанных результатов: отвергнуто; подтверждение —
  отдельный переход, словарные кандидаты не являются подтверждёнными кодами.

Серверный способ развёртывания дополнен [ADR 0010](0010-docker-compose-ansible.md):
полный Compose-стек с контейнерным inference и Ansible. Хостовый Mac LLM остаётся
только вариантом development-стенда.

## Пределы

PDF/PNG/JPEG до 20 МиБ, до пяти страниц PDF, ограничены текст, количество строк,
выход worker, таймаут и очередь владельца. Произвольные документы могут требовать
полного ручного заполнения. Значения, единицы и референсы не конвертируются и
не оцениваются по клиническим нормам. ASR, внешний AI API, автономный mobile runtime,
синхронизация черновиков/записей и потребитель серверного outbox ещё не реализованы.

Bootstrap доступа остаётся development-механизмом ADR 0008. Право на запуск
серверного задания использует `cloud_enabled` и проверяется при приёме; отзыв
доступа блокирует чтение производных. Уже принятое задание может закончить вычисление.
Боевые аккаунты, отдельное processing entitlement, шифрование и политика удаления
производных требуют следующих решений. Закрытие экрана сохраняет задание в живом
приложении; фоновые вычисления после остановки ОС не обещаются.
