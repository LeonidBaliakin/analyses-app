# Облачные права и квоты

Реализовано 26 ноября 2026 года. [ADR 0013](adr/0013-cloud-rights-and-quotas.md),
[HTTP-контракт](../contracts/openapi/cloud-access.yaml).

В **Настройки → Вход и устройства** после входа появляется блок облачных возможностей:
синхронизация, хранение оригиналов и серверное распознавание. Для каждого показаны
доступ и расход; оригиналы и распознавание отдельно показывают резерв. «Обновить права
и расход» запрашивает свежую сводку. После ошибки прежние числа явно помечаются как
последние известные, сервер всё равно проверяет право перед операцией.

Стартовые пилотные лимиты: 10 000 активных записей, 1 ГиБ исходных файлов,
100 успешных распознаваний за месяц UTC. Это ещё не платный тариф.

- При заполнении sync quota новые локальные записи сохраняются, отправка остаётся
  в outbox. После увеличения лимита нажмите повтор синхронизации. Правки существующих
  записей и удаления не увеличивают расход; при полном отзыве sync права запрещены
  все облачные изменения, но pull и локальная работа остаются доступны.
- Storage quota считает ready и reserved bytes. Повтор загрузки не списывает их
  дважды. Исчерпание квоты сохраняет локальный оригинал. Понижение лимита/отзыв не
  удаляет готовые файлы; скачивание остаётся доступным при доступе к профилю.
- Распознавание резервирует slot при приёме задания, а учитывает успешный результат
  при ready. Отмена/ошибка освобождают резерв. Повтор того же jobId не расходует новый
  slot. Резерв закреплён за месяцем приёма, включая завершение в следующем месяце.
  Уже сохранённые черновики можно получить после запрета новых обработок.

Срок доступа проверяется на сервере. Подписка, платежи и восстановление покупки не
входят в этот этап. Локальный режим не требует облачной подписки; отказ не включает
другой AI-провайдер и не меняет подтверждённые медицинские записи.

## Изменение политики оператором

Entitlements не имеет host-порта. Оператор выполняет внутри Compose:

```bash
docker compose exec -T entitlements /app/entitlements --grant < grant.json
```

Пример только для синтетического владельца (настоящие идентификаторы не коммитьте):

```json
{
  "ownerId": "synthetic-owner",
  "operationId": "synthetic-grant-001",
  "baseRevision": 1,
  "policy": {
    "syncEnabled": true,
    "storageEnabled": true,
    "processingEnabled": false,
    "recordLimit": 10000,
    "storageLimitBytes": 1073741824,
    "processingMonthlyLimit": 100,
    "validUntil": null
  }
}
```

Текущую revision своего тестового аккаунта можно посмотреть в авторизованном
`GET /v1/profiles/{profileId}/cloud-access`. Административный ключ остаётся в контейнере;
клиент не получает его. Повтор операции требует того же ID и payload; новое изменение
требует нового ID и текущей revision. Срок задаётся ISO 8601 с UTC/offset либо null.

## Развёртывание и проверки

Сервис Entitlements, отдельная БД, два разных persistent ключа чтения/grant,
AOT-образ, healthcheck и Ansible входят в оба Compose workflow. Для существующего
локального стенда сначала выполните `python3 infra/documents/init_accounts.py`, затем
обновите сервисы через Compose. Скрипт добавляет новые ключи без смены прежних.

Из `apps/health_app` против локального Ansible `server-check`:

```bash
dart run tool/cloud_access_smoke.dart
```

Probe временно меняет политику синтетического bootstrap-владельца и восстанавливает
её в finally. Он оставляет синтетический результат и PDF в dev-стенде, проверяет
реальные HTTP, SQLite/outbox, увеличение квоты и повтор, независимые разрешения,
доступность исходника после отзыва и SHA-256. Не запускайте на боевых данных.
[Фактические проверки и ограничения](reports/cloud-access-2026-11-26.md).
