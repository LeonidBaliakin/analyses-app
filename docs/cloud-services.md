# Облачные микросервисы и серверная обработка

Облачная часть разделяется по независимым данным, внешним API и вычислительным ресурсам. Каналы уведомлений и источники импорта получают отдельные адаптеры и очереди. На сервере предусматривается обязательный контур обработки документов и результатов через собственную LLM или внешний API; локальный контур приложения сохраняется для офлайна.

Это целевая схема. Сервисы, каналы и коннекторы включаются по мере реализации; исходный код и инфраструктура ещё предстоят. Прикладные сервисы планируются на Dart, специализированные OCR/LLM runtimes используют подходящие для своих движков технологии.

## Прикладные сервисы

| Сервис | Владеет и отвечает за |
|---|---|
| `identity` | Учётные записи, способы входа, устройства и сессии |
| `access-sharing` | Разрешения на профили и документы, ограниченные ссылки, отзыв и журнал доступа |
| `health-records-sync` | Профили, сдачи, результаты, события, препараты, дневники, подтверждённые изменения и журнал синхронизации |
| `documents` | Оригиналы, метаданные, загрузочные сессии, состояние облачной копии и учёт объёма; байты в SeaweedFS OSS |
| `billing-entitlements` | Проверенные покупки, продления, возвраты, тарифы и права на облачные функции |
| `terminology` | Медицинские понятия, специальности, МКБ, синонимы источников, опубликованные редакции и офлайн-пакеты словарей |
| `provider-directory` | Канонический каталог лабораторий, врачей, адресов, услуг и предложений со временем актуальности |
| `model-catalog` | Манифесты AI-пакетов, совместимость, версии и каналы установки |

`identity` устанавливает личность, `access-sharing` разрешает операцию с ресурсом, `billing-entitlements` задаёт облачные возможности. Эти проверки используются сервисом, владеющим ресурсом. Результаты и журнал синхронизации сохраняются транзакционно в `health-records-sync`.

## Уведомления по каналам

`notification-orchestrator` принимает события, учитывает настройки пользователя, формирует намерение отправки, выбирает шаблон и канал, планирует время и отслеживает итог доставки.

Каждый канал получает собственный worker/service: `delivery-telegram`, `delivery-whatsapp`, `delivery-max`, `delivery-email`, `delivery-push`; другие каналы добавляются тем же способом. Это варианты подключения, а не уже выбранные и настроенные провайдеры.

Канальный сервис владеет интеграцией с API провайдера, привязками получателей, ограничениями скорости, секретами и обработкой callback/webhook. Общие контракты задают `notificationId`, адресата, канал, шаблон, полезную нагрузку и ключ идемпотентности. Orchestrator хранит намерение и сводное состояние; канал возвращает статус и идентификатор провайдера через контракт.

Очереди, повторы и лимиты разделены по каналам. Неопределённый результат отправки после таймаута учитывается отдельно от однозначного отказа: стратегия повторов зависит от возможностей провайдера. Callback проверяется, а локальные повторы не создают новые намерения отправки.

Содержание уведомлений определяется шаблонами и настройками. Базовый сценарий — сообщение о событии со ссылкой в приложение; пересылка оригиналов и медицинских значений является отдельным разрешённым действием.

API и доступность каналов проверяются при подключении. Примеры официальных интерфейсов: [Telegram Bot API](https://core.telegram.org/bots/api), [MAX Bot API](https://dev.max.ru/docs-api). Регистрация, правила и стоимость конкретного провайдера не считаются одинаковыми для разных каналов.

## Парсинг сайтов и внешние системы

`connector-orchestrator` хранит реестр источников, задания, расписания, разрешённые режимы доступа и состояние импорта. Для каждого сайта или API создаётся `connector-{source}` с собственной конфигурацией, очередью, контрольной точкой и версией парсера.

Коннектор получает данные разрешённого источника, сохраняет нужный исходный материал, разбирает его и выдаёт стандартный результат со ссылкой на источник и временем получения. При наличии подходящего API используется API; особенности HTML и браузерного рендеринга остаются внутри конкретного коннектора.

Публичные каталоги услуг и цен, справочники и импорт медицинских результатов являются разными типами заданий. Для личных результатов проверяются учётная запись, профиль и право пользователя подключить источник. Данные не смешиваются между владельцами.

`provider-directory` принимает проверенные предложения услуг и контакты. Медицинские документы идут через `documents` и конвейер обработки. Термины сопоставляются через `terminology`. Коннектор не пишет напрямую в таблицы медицинских записей.

Изменения разметки проверяются на сохранённых примерах; публикация новой версии коннектора независима от остальных источников. При неполном ответе поле сохраняется как неизвестное. Для каждого источника задаются лимиты, таймауты и допустимая область адресов.

## Серверный OCR и LLM

| Сервис или worker | Ответственность |
|---|---|
| `processing-orchestrator` | Задания, этапы, состояние, разрешённый режим обработки, повторы, отмена и сохранение версии результата |
| `document-preprocessor` | Определение типа, извлечение текстового слоя, подготовка страниц и изображений с сохранением исходника |
| `ocr-worker` | Распознавание страниц и координат текста; масштабируется под CPU/GPU и выбранный движок |
| `asr-worker` | Транскрипция загруженного аудио, если выбран серверный голосовой ввод |
| `lab-results-parser` | Черновики лабораторных результатов: названия, значения, единицы, референсы, даты и привязка к источнику |
| `discharge-parser` | Черновики сведений из выписок и заключений: события, назначения и связанные показатели |
| `medical-events-parser` | Черновики событий из текста или транскрипции |
| `inference-gateway` | Единый интерфейс вызова собственных LLM и внешних API, возможности, лимиты, маршрутизация и сведения об исполнении |
| `llm-runtime-{model}` | Загрузка и выполнение конкретной серверной модели, управление вычислительными ресурсами |

Worker может быть самостоятельным процессом без собственной БД: он получает задачу и возвращает артефакт или событие. Состоянием обработки владеет orchestrator. Разные workers могут собираться из общего кода и выпускаться отдельными deployments с собственными очередями и ресурсами.

Для self-hosted LLM рассматривается [vLLM с совместимым HTTP-интерфейсом](https://docs.vllm.ai/en/latest/serving/online_serving/openai_compatible_server/). Другой runtime или внешний API подключается через тот же шлюз, если соответствует требуемому контракту. Модель, лицензия, память и аппаратное обеспечение проверяются отдельно.

Режим обработки задаётся явно: на устройстве, на собственном сервере либо через разрешённого внешнего провайдера. Переход от self-hosted к внешнему API не происходит скрыто. Обычная загрузка оригинала в облачное хранилище не является запросом на обработку.

## Сквозной конвейер документа

1. Documents подтверждает готовность конкретного `originalId`.
2. По запросу пользователя или выбранному правилу создаётся идемпотентное задание с профилем, исходником, режимом, типом разбора и редакцией словарей.
3. Подготовка извлекает текст; OCR выполняется для страниц, которым он нужен. Артефакты сохраняются отдельно от исходника.
4. Специализированный parser вызывает inference gateway и получает структурированные кандидаты.
5. Значения и единицы проверяются медицинскими правилами; названия сопоставляются с закреплённой редакцией Terminology.
6. Orchestrator сохраняет черновик, версии моделей и правил, источник каждого поля и неоднозначные соответствия.
7. Пользователь исправляет и подтверждает черновик. Подтверждённые записи попадают в Health Records через идемпотентную команду.
8. События готовности и синхронизации могут породить уведомления по подключённому каналу.

Структурированный формат ответа ограничивается схемой. [vLLM поддерживает structured outputs](https://docs.vllm.ai/en/latest/features/structured_outputs/), но соответствие JSON Schema не подтверждает правильность чисел, дат или медицинского смысла. Эти проверки и подтверждение являются самостоятельными этапами.

Локальный и серверный конвейеры возвращают одинаковый контракт черновика и допускают разные реализации OCR/LLM. Повторный запуск создаёт новую версию обработки и не затирает оригинал или исправления пользователя. Если запись уже подтверждена локально, синхронизация связывает её происхождение без повторного создания результата.

## Контракты заданий

Предлагаемый внешний интерфейс:

- `POST /documents/{documentId}/processing-jobs`: запрос обработки конкретного оригинала и режима.
- `GET /processing-jobs/{jobId}`: этап, прогресс, ошибка и ссылка на черновик.
- `POST /processing-jobs/{jobId}/cancel`: запрос отмены.
- `GET /processing-jobs/{jobId}/draft`: структурированные кандидаты и происхождение.
- `POST /drafts/{draftId}/confirm`: подтверждение с идентификатором операции и ожидаемой ревизией.

Пример событий: `DocumentReady`, `ProcessingRequested`, `ProcessingStageCompleted`, `DraftReady`, `RecordsConfirmed`, `NotificationRequested`, `DeliveryStatusChanged`, `TerminologyReleasePublished`. События несут ссылки и версию схемы; большие файлы остаются в хранилище.

## Изоляция и согласованность

- Каждый сервис управляет собственным состоянием и миграциями; workers изменяют чужое состояние через контракт.
- Отдельные очереди используются для каждого канала, источника и тяжёлого этапа обработки; одни и те же парсеры не требуют выделенного GPU на каждый экземпляр.
- Важные изменения и события фиксируются через транзакционную исходящую очередь. Обработчики и команды допускают повторную доставку.
- Доступ к исходнику разрешается по заданию и профилю; provider-ключи остаются на сервере.
- Для разбора фиксируются версии схемы, parser, модели, запроса, OCR и словаря; исходные ответы и исправления имеют установленный срок хранения.
- Долгие задания имеют таймаут, состояние отмены и возможность продолжить после перезапуска. Ошибка доставки уведомления не отменяет подтверждённую медицинскую запись.

## Порядок реализации

Первый сквозной срез: Documents и SeaweedFS, Terminology с минимальным словарём, обработка одного типа бланка через собственную LLM или выбранный API, проверка черновика и Health Records & Sync. Затем добавляются отдельные parser-ветки, один канал уведомлений и один внешний источник. Новые каналы и источники подключаются независимо по уже проверенным контрактам.

Карты ядра и UI: [core-modules.md](core-modules.md), [ui-architecture.md](ui-architecture.md). Словари и оригиналы: [terminology.md](terminology.md), [document-storage.md](document-storage.md).
