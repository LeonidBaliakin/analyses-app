# Сводка, отчёт и синхронизация записей

Рабочий срез пункта 6, 25 ноября 2026 года. [ADR 0011](adr/0011-period-reports-and-record-sync.md),
[OpenAPI](../contracts/openapi/records.yaml), [результаты проверок](reports/records-sync-2026-11-25.md).

## В приложении

«Сводка» показывает количество результатов, пересекающихся курсов и измерений
за выбранный период, до восьми последних групп показателей. Из неё открывается
единая «История анализов» (`/history`). Кнопка QR в шапке открывает отдельный
раздел «Доступ по ссылке и QR»; пример ссылки и QR явно обозначен демонстрационным.

История использует общий `history` UI для подтверждённых локальных данных и
отдельного синтетического примера. По умолчанию показана вся история; доступны
последняя сдача, две последние и включительный диапазон YYYY-MM-DD. Можно выбрать
несколько показателей через поиск; плашки выбора остаются после сворачивания
поиска. Названия строк и шапка дат закреплены, доступны горизонтальная прокрутка,
ручной поворот просмотра и подробности исходного результата.

Группировку совместимых реальных результатов по-прежнему выполняет `HealthReport`
в ядре: неизвестные соответствия и неполные сведения о методе/материале не
объединяются по похожему названию. Повторные результаты одной даты сохраняются
в ячейке и экспорте. Произвольные референсы не интерпретируются UI автоматически.
На график событий включаются пересекающиеся курсы, в том числе начатые до периода,
и домашние измерения с исходной датой и сохранённым временем/UTC offset. В
демопримере дополнительно видны исходные болезни, жалобы и госпитализации;
новый тип подтверждённой записи для них этот UI-срез не вводит.

Печать использует те же выбранные строки и даты, что и экран. События включаются
при открытом графике. Профиль, исходные значения, единицы, референсы, сведения об
источнике, заметки и известный фрагмент документа сохраняются. Ошибочные даты
блокируют экспорт. Удаления и AI-черновики не включаются.

На web/desktop кнопка «Печать / PDF» сохраняет печатную версию HTML с кнопкой
печати; откройте файл браузером и выберите «Печать → Сохранить как PDF».
Android/iOS не поддерживают выбор места сохранения в текущем `file_selector`:
UI показывает это состояние и позволяет явно скопировать текст выбранного
отчёта в буфер. Встроенный native PDF-export пока отсутствует. Оригинальные
PDF/фото не встраиваются, экспорт не отправляет данные серверу или врачу.
Реальные ссылки доступа врачу остаются отдельной нереализованной интеграцией.

Кнопка «Синхронизация записей» доступна и при пустом локальном профиле — второе устройство
может получить профиль из облака. Обычный вход теперь находится в [аккаунтах и сессиях](accounts-and-sessions.md);
подключение выполняется отдельной кнопкой после входа. Техническая форма адреса Documents
и bearer token сохранена для dev-совместимости. Такое подключение
явно включает обмен; token остаётся в памяти, после перезапуска нужно подключиться снова.
Сохранение локально доступно при отключении сети или запрете облачных прав.

Показываются очередь ожидающих операций, число конфликтов, время последнего завершённого
обмена и следующего повтора. Завершённый обмен не означает, что конфликтные записи
подтверждены сервером: их очередь/счётчик остаются видимыми. «Синхронизировать / повторить»
доступно для явного повтора; автоматический опрос выполняется раз в 30 секунд при открытом
приложении. Сбой, отмена соединения или потеря ответа не очищают очередь.

Конфликт показывает значения на устройстве и сервере, включая признак удаления.
Выберите одну полную версию. Локальная версия отправляется новой операцией; серверная
применяется локально без обратной отправки. Выбор локальной после серверного удаления
означает восстановление. При новой гонке выбор потребуется снова. Старые локальные
версии остаются в record_history, полученные серверные — в sync_remote_history;
отдельного UI архива удалённых записей и разрешённых конфликтов пока нет.

## Протокол и схема

SQLite schema 5 сохраняет старые записи, originals, draft history и outbox byte-for-byte.
Новые таблицы: sync_scopes, sync_versions, sync_attempts, sync_acks, sync_conflicts,
sync_remote_history. Локальная ревизия редактора отличается от серверной version.
Отправленная операция сохраняет исходный operationId и подготовленную базу. Успешный
повтор возвращает тот же receipt; другой payload под прежним ID отвергается.
Привязка защищает профиль от случайного обмена с другим аккаунтом/endpoint.

API имеет schemaVersion 1. `GET sync-access` возвращает owner/profile/epoch/canWrite.
`POST sync-operations` принимает operationId/deviceId/baseVersion/payload/deleted/epoch,
возвращает applied и current. Конфликт возвращается как receipt с applied=false;
это не успешная запись медицинских данных. GET sync-changes принимает cursor/epoch
и возвращает упорядоченные records, новый cursor и more. Изменение записи/receipt/
change log/server outbox атомарно. Отзыв прав проверяется и на повторе.

Медицинские DTO форматов 1/2/3 общие для клиента и сервера через `record_sync`.
Проверяются медицинские поля и происхождение. Синхронизация documentSource не скачивает
и не публикует исходные байты: доступность оригинала проверяется отдельно через Documents.
События RecordChanged сейчас сохраняются в outbox, потребитель уведомлений не подключён.

Ограничения: запрос операции до 256 КиБ; pull до 100 событий / 3 МиБ; клиент до 100
отправок за проход и до 50 страниц pull. Остаток очереди продолжает следующий проход.
Серверные права и лимит активных записей проверяются через
[Entitlements](cloud-access.md). Платёжные тарифы появятся позже. 401/403 и несовместимость протокола требуют вмешательства, автоматический
retry их не скрывает. История пока не сжимается и не очищается.

## Запуск

Все серверные процессы — Docker Compose; host daemon приложения не нужен.
Для development из `infra/documents`:

```bash
docker compose --profile sync up -d --build documents records
```

Одноразовый `records-db` создаёт отдельную БД `records`; PostgreSQL и SeaweedFS используют
существующие volumes. Records API не имеет host-порта, клиент обращается к Documents
`http://127.0.0.1:18088`. Адрес, токен и CORS — как в [Documents](../services/documents/README.md).

Для сервера — [Ansible](../infra/ansible/README.md). Роль копирует общие чистые Dart-пакеты,
собирает `services/records`, запускает records-db/records и проверяет sync-access.
Старые volumes и bootstrap-секреты сохраняются при обновлении.

## Проверка

Пакеты проверяются через Dart/Flutter MCP. Для PostgreSQL-тестов создайте **отдельную** БД:

```bash
# Из infra/documents:
docker compose exec -T postgres createdb -U documents records_tests
```

`services/records/test` очищает только records_tests; штатная records не очищается.
Проверены права, повтор/изменённый ID, конкурентные CAS, удаления, явное восстановление,
атомарный откат при сбое outbox, SQLite restart/backoff, потеря ACK, два клиента,
обе ветви конфликта, опоздавший ответ, миграции и границы периода.

Сквозной probe из `apps/health_app` против отдельного Ansible deployment:

```bash
dart run tool/records_sync_smoke.dart /absolute/path/to/deployment
```

По умолчанию использует `.runtime/server-check`. Читает его секреты без вывода в лог,
работает только с синтетическими записями, использует два отдельных SQLite-файла,
проходит через Documents HTTP proxy и настоящий records/PostgreSQL. Проверяет,
что оба устройства формируют одинаковый отчёт после обмена и выбора конфликтов.
Новые синтетические записи остаются в указанном стенде; используйте отдельный deployment.
