# Проверка OCR/LLM рабочего среза, 24 ноября 2026

Синтетические материалы без данных пациентов. Реальные Tesseract, llama.cpp и
Documents/PostgreSQL/SeaweedFS; общий Dart-валидатор из приложения.
[Машиночитаемый результат с SHA-256 входов и версиями](processing-pilot-2026-11-24.json),
[воспроизведение](../document-processing.md#воспроизведение-проверки).

## Условия

Mac, Apple M5 Pro, 48 ГиБ RAM, macOS 26.7.1. Qwen2.5-1.5B-Instruct Q4_K_M,
1 117 320 736 байт, SHA `6a1a2eb6d15622bf3c96857206351ba97e1af16c30d7a74ee38970e434e9407e`.
llama.cpp b12359, Metal, ctx 8192, parallel 1, threads 4, temperature 0, seed 42,
max_tokens 1600. Schema-constrained JSON и одинаковый prompt/worker для обоих путей.
Локальный Tesseract 5.5.4, серверный 5.5.0, одинаковые закреплённые rus+eng tessdata.
Серверный OCR/worker работает в Docker, его LLM — этот же собственный Mac runtime.
Измерения не сравнивают два независимых GPU/сервера.

Пять входов генерируются Pillow 12.0.0 и macOS Arial: RU PNG с двумя результатами,
тот же растровый бланк в PDF, EN качественный результат без даты, RU с инструкциями
отправить документ и выполнить команды, белый лист. Даты PDF закреплены. SHA входов
и полные runtime IDs находятся в JSON. Времена — по одному полному запуску на вход;
серверное время включает загрузку, верификацию Documents и polling. Это не статистика
перцентилей или медицинский benchmark. Ранее холодный запуск PDF занял 11,65 с;
приведённый окончательный прогон использует прогретые компоненты.

## Поля и время

Считаются пять полей строки: название, значение/знак/точность, единица, референс, дата.
OCR-ошибка означает отсутствие ожидаемой непустой строки в распознанном тексте;
ошибка LLM — несовпадение поля с разметкой, включая ошибки, унаследованные от OCR. Последняя колонка — несовпадение после
общего валидатора, до ручной правки. Для базового RU/PDF ожидается по десять полей,
для EN и injection — по пять. Таблица не измеряет клиническую правильность.

| Вход | Режим | Время, с | Ошибки OCR | Ошибки LLM | Ошибки полей проверки |
|---|---|---:|---:|---:|---:|
| RU PNG | локальный | 1,438 | 0 | 0 | 0 |
| RU PNG | серверный | 1,845 | 1 | 1 | 1 |
| RU PDF | локальный | 1,356 | 1 | 8 | 8 |
| RU PDF | серверный | 1,519 | 1 | 8 | 8 |
| EN, качественный, без даты | локальный | 0,645 | 0 | 0 | 0 |
| EN, качественный, без даты | серверный | 1,195 | 0 | 0 | 0 |
| RU, вредоносные инструкции | локальный | 0,716 | 0 | 4 | 4 |
| RU, вредоносные инструкции | серверный | 1,369 | 1 | 1 | 1 |
| Белый лист | локальный | 0,114 | — | — | `unreadable` |
| Белый лист | серверный | 0,701 | — | — | `unreadable` |

Серверный OCR прочитал `г/л` как `Гл`; PDF — как `r/n`. В PDF LLM объединила значение,
единицу и референс, пропустила дату. На injection локальная LLM также неверно разделила
колонки. Смешанные числовые поля после общего валидатора остаются пустыми и требуют ручной
правки; исходное предложение сохраняется. Неверно выбранная единица/референс всё ещё
может совпасть с реальным текстом OCR. Привязка к источнику не доказывает семантику.
Требуется ручная проверка; эта модель не принята для автоматического медицинского импорта.
Ни одно задание не подтверждает запись автоматически. Вредоносный текст не получает
инструменты/команды/сетевые адреса: worker обращается только к заданному собственному LLM.

Дата EN остаётся неизвестной; подтверждение до её явного ввода заблокировано.
Пустой лист сохраняет OCR-артефакт и ошибку, медицинские результаты не создаёт.
Отдельные fault-проверки проверяют выдуманную единицу/дату, потерю `<` или хвостовых
нулей: такие поля сохраняются как отклонённые предложения и не предзаполняются.

## Память и ограничения

Максимальный наблюдавшийся RSS llama-server при опросе каждые 100 мс —
1 657 312 КиБ, около 1,58 ГиБ. Это RSS процесса, не суммарный пик приложения,
OCR subprocesses, Docker VM и Metal allocation. Холодная загрузка модели до запуска
опроса не включена. Такой замер не доказывает пригодность на телефоне и не заменяет
профилирование единой памяти GPU. На Android/iOS измерений нет.

## Поведение приложения и отказы

Реальный `tool/processing_smoke.dart` прошёл для local и ownServer: исходные байты →
OCR/LLM → общий черновик → изменение 140 на 141 → перезапуск SQLite → подтверждение
и повтор. Исходное 140 остаётся в documentSource, `< 0,0100` сохраняется, оригинал
проверен по SHA-256, повтор подтверждения и новый разбор того же оригинала не создают
второй результат. Соответствие словарю выбирается явно.

SQLite-тест воспроизводит падение посреди создания нескольких результатов: текущие
записи, история, outbox и маркер подтверждения откатываются вместе. Проверены конфликт
редакций, потерянный ответ подтверждения, защита source, переход schema 3→4 и прежние
миграции. Серверные тесты используют отдельный PostgreSQL: доступ/профиль, конкурентный
повтор, изменённый fingerprint, SHA, entitlement, лимит очереди, отмена, сохранение OCR
при сбое LLM и восстановление прерванного задания. Widget-тест проверяет RU/EN, правку,
сохранение/подтверждение и изменение размера со сгибом. Web запущен, hot reload прошёл.

Реальный fault probe дополнительно проверяет неверный SHA-256, неподдерживаемый MIME,
повреждённый PNG и SIGTERM с очисткой временного OCR-каталога.

Сборка UI и CLI helper не доказывают возможность запуска helper в подписанном macOS
sandbox. Автономные mobile/browser модели, внешние AI API, ASR, синхронизация,
длительные нагрузочные испытания отсутствуют. Полный контейнерный CPU deployment
с Ansible добавлен отдельно — [проверка развёртывания](server-deployment-2026-11-24.md);
приведённые выше измерения относятся к первоначальному Mac/Metal development-стенду.
