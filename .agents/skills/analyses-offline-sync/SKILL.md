# Офлайн и синхронизация

Прочитай разделы локального хранения и синхронизации в [архитектуре](../../../docs/architecture.md), границы [общих модулей](../../../docs/core-modules.md) и фактическую схему/протокол, если они уже созданы.

## Выполнение

1. Определи локального владельца записи, стабильный ID, версию схемы и источник истины для каждого поля. Чтение UI и обычное сохранение выполняются локально без проверки наличия сети или активной облачной подписки.
2. Запиши изменение и outbox в одной транзакции. Опиши поведение после сбоя до/после commit, повторной команды и перезапуска приложения. Отдельный файл и SQL-транзакция требуют состояния восстановления, поскольку не имеют общей атомарной записи.
3. Для отправки задай устойчивый ID операции, порядок зависимостей, идемпотентность сервера и обработку потерянного ответа. Для получения — курсор, ревизии и транзакционное применение изменений.
4. Определи конфликт на уровне изменяемых данных и tombstone удаления. Время устройства не выбирает победителя молча. Подтверждённые медицинские изменения не теряются при конфликте; спорная версия сохраняется для разрешения.
5. Реализуй повторы с ограничением частоты и явными постоянными ошибками. Серверный отказ в доступе или квоте не удаляет локальную запись. Подписка управляет облачными правами, а не возможностью вести локальные данные.
6. Для миграции сохраняй исходные данные и проверяй переход с поддерживаемой версии. Для web учти выбранный SQLite/Wasm backend, конкурирующие вкладки, ограничения хранилища и возможную очистку данных браузером.
7. Покажи пользователю состояние синхронизации и восстановимый сбой. Не помечай запись сохранённой в облаке до подтверждения сервера.

## Проверка

Проверь относящиеся к изменению границы: нет сети → сохранение → перезапуск; восстановление outbox; повтор операции после потери ответа; конкурирующие правки; удаление с другого устройства; прерывание и миграция. Используй реальные транзакции целевого хранилища там, где fake не выявит ошибку атомарности.

Если затронуты оригиналы, добавь workflow `analyses-original-storage`: синхронизация записи сама по себе не доказывает доступность байтов документа.

Результат задачи: сохранение и восстановление без потери данных, описанная совместимость протокола/схемы и проверки характерных сбоев.
