# Облачный сервис или worker

Прочитай [облачную архитектуру](../../../docs/cloud-services.md) и [границы общих модулей](../../../docs/core-modules.md). Список предложенных сервисов не требует их одновременного создания.

## Выполнение

1. Определи ответственность, владельца данных и причину отдельного развёртывания: права, нагрузка, зависимости или жизненный цикл. Для нового мессенджера/сайта используй границу существующего оркестратора и отдельного delivery/connector worker, если она уже реализована.
2. Зафиксируй контракт: OpenAPI для HTTP, схему события/задания для очереди, ошибки, версии, idempotency key и correlation ID. Сохрани совместимость установленных клиентов и потребителей либо опиши переход.
3. Проверяй аккаунт, профиль, разрешение операции и облачные права на сервере. Сервис не читает таблицы соседа напрямую. Общие Dart-пакеты не переносят ORM-модели и внутренние таблицы в публичный API.
4. Свяжи запись данных и исходящее событие через транзакционный outbox. Обработчик допускает повтор доставки; внешний вызов имеет таймаут, ограничения повторов и состояние неопределённого результата. Не обещай exactly-once эффект у провайдера без подтверждённой поддержки.
5. Для канала доставки реализуй receipt/callback отдельно от постановки в очередь. Для коннектора отдели получение источника, курсор и идентификацию документов от медицинского парсинга; повторы не создают дубликатов.
6. Для подписки проверяй событие платёжного провайдера, его уникальность, восстановление покупки и серверный пересчёт entitlements. Не блокируй локальную работу окончанием подписки.
7. Добавь структурированные технические метрики и логи без содержимого документов, секретов и медицинских значений. Секреты задаются окружением/хранилищем секретов; включение доставки не означает разрешения отправить пробное реальное сообщение.

## Проверка

Проверь существенные границы: чужой профиль, повтор задания/webhook, потерянный ответ внешнего API, таймаут, несовместимая схема и восстановление после перезапуска. Контрактный тест должен проверять наблюдаемое поведение потребителя, а не только сериализацию текущего класса.

Внешний API для разработки подменяй локальным сервером или тестовым окружением, пока задача не разрешает реальные внешние эффекты. Для контейнеров используй доступный Docker-workflow по необходимости.

Результат задачи: самостоятельная ответственность, проверяемый контракт, корректные повторы и документированные эксплуатационные ограничения.
